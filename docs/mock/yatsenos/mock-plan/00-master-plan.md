## 1. 项目概述

将中山大学操作系统课程（YatSenOS）的 9 个实验（0x00-0x08）模拟为一个为期 18 周的长程软件开发项目，生成飞书多模块的模拟数据，用于测试飞书记忆系统。

### 1.1 项目映射关系

| 实验编号 | 项目阶段 | 阶段名称 | 核心交付物 |
|---------|---------|---------|---------|
| 0x00 | Phase 0 | 基础设施搭建 | 开发环境、Rust 工具链、CI 流水线 |
| 0x01 | Phase 1 | 引导加载器 | UEFI Bootloader、ELF 加载、串口驱动 |
| 0x02 | Phase 2 | 中断与异常处理 | IDT/APIC/GDT、时钟中断、输入驱动 |
| 0x03 | Phase 3 | 进程调度引擎 | 进程模型、上下文切换、FIFO 调度器 |
| 0x04 | Phase 4 | 用户态运行时 | 用户/内核态切换、系统调用、Shell |
| 0x05 | Phase 5 | 并发与同步原语 | fork、自旋锁、信号量、阻塞/唤醒 |
| 0x06 | Phase 6 | 存储子系统 | ATA 驱动、MBR 分区、FAT16 文件系统 |
| 0x07 | Phase 7 | 内存管理优化 | 帧回收、栈增长、brk 系统调用 |
| 0x08 | Phase 8 | 特性扩展冲刺 | VGA/tmpfs/分配器/缓存/多核（选做） |

## 3. 时间线设计

### 3.1 总时间跨度：18 周

模拟时间从 2026-03-02（周一）到 2026-07-03（周五），共 18 个教学周。

### 3.2 各阶段时间安排

| 阶段 | 周次 | 起止日期 | 关键里程碑 |
|------|------|---------|---------|
| Phase 0 | W1-W2 | 03/02 - 03/13 | 环境就绪、首次 CI 通过 |
| Phase 1 | W2-W4 | 03/09 - 03/27 | UEFI 启动成功、串口输出 |
| Phase 2 | W4-W6 | 03/23 - 04/10 | 中断注册完成、时钟中断跑通 |
| Phase 3 | W6-W8 | 04/06 - 04/24 | 进程创建与切换、调度器就绪 |
| Phase 4 | W8-W10 | 04/20 - 05/08 | 用户态 Shell 可交互 |
| Phase 5 | W10-W12 | 05/04 - 05/22 | fork 成功、并发程序可运行 |
| Phase 6 | W12-W14 | 05/18 - 06/05 | 文件系统挂载、可读磁盘文件 |
| Phase 7 | W14-W16 | 06/01 - 06/19 | 内存回收、栈增长、brk 就绪 |
| Phase 8 | W16-W18 | 06/15 - 07/03 | 选做特性完成、最终演示 |

**注意**: 各阶段有 1-2 周重叠期，模拟真实项目中前后阶段衔接的场景。

### 3.3 每个阶段内部节奏

每个阶段（2-3 周）的内部节奏如下：

```
Week 1 前半: 启动会 -> 需求分析 -> 方案设计
Week 1 后半: 核心编码 -> 首次联调
Week 2 前半: 功能完善 -> 代码审查 -> 冲突讨论
Week 2 后半: 测试修复 -> 文档更新 -> 阶段总结
Week 3 (若有): 收尾优化 -> 交接 -> 下阶段预热
```

## 6. 决策冲突与真实场景设计

### 6.1 冲突类型与触发点

| 冲突类型 | 触发阶段 | 具体场景 | 涉及人员 | 持续时长 |
|---------|---------|---------|---------|---------|
| 技术方案分歧 | Phase 1 | ELF 加载方式争论 | P1 vs P3 | 2天 |
| 架构选型冲突 | Phase 3 | 进程模型设计（Linux式 vs Windows式） | P2 vs P3 | 3天 |
| 资源分配争议 | Phase 5 | fork 实现策略（简化 vs 完整） | P3 vs P4 | 2天 |
| 代码风格分歧 | Phase 6 | 错误处理方式（unwrap vs Result 传播） | P5 vs P6 | 1天 |
| 优先级冲突 | Phase 7 | 内存回收算法选择 | P8 vs P1 | 2天 |
| 交付压力冲突 | Phase 8 | 选做功能范围争论 | 全员 | 3天 |

### 6.2 废话与闲聊场景

- 每个阶段群聊中约 15-20% 的消息为非技术闲聊
- 闲聊触发点：周五下午、阶段性突破后、深夜加班时
- 闲聊内容：吐槽食堂、分享技术段子、讨论考试安排、约饭、转发技术新闻

### 6.3 真实项目节奏模拟

- 代码提交后的"我这边通过了，你们试试"
- 突然发现的 bug 导致的紧急讨论
- 临近 deadline 时的"这个功能先不做了"
- 周末突然的灵感分享
- "这个我之前遇到过，解决方案是..."

## 8. 执行策略

### 8.1 数据生成顺序

1. **准备阶段**: 初始化所有配置目录并登录对应的飞书账号
2. **Phase 0 (第1天)**: 创建知识库 + 发送启动消息 + 创建任务清单
3. **Phase 0-8 (持续)**: 按时间线在对应群聊中发送 lark-im 消息（切换对应配置目录）
4. **每个阶段开始**: 创建 lark-task 任务和子任务
5. **每周**: 安排 lark-calendar 日程（周会）
6. **每个阶段关键节点**: 创建 lark-doc 文档
7. **持续演进**: 更新 lark-wiki 知识库结构
8. **每个阶段结束**: 更新 lark-base 多维表格和 lark-sheets 电子表格
9. **周会时**: 创建 lark-vc 视频会议记录和 lark-minutes 妙记

### 8.2 消息发送节奏

- 群聊消息：工作日每天 5-15 条/群，周末 0-3 条/群
- 任务创建：每个阶段 3-5 个主任务，每个主任务 2-4 个子任务
- 日程安排：每周 1-2 个日程（周会 + 按需的技术评审）
- 文档创建：每个阶段 2-4 个文档
- 知识库更新：每个阶段 1-2 次结构调整

## 9. 注意事项

### 9.1 配置目录管理

- 妥善保管所有 ~/.lark-cli-p1 到 ~/.lark-cli-p8 目录
- 定期备份配置目录，避免意外丢失
- 可以使用符号链接或 git 管理配置

### 9.2 消息真实性

- 避免过于完美的对话
- 包含打字错误、撤回消息等细节
- 包含闲聊和废话
- 包含冲突和争论

### 9.3 时间合理性

- 消息时间要符合学生作息
- 避免凌晨 3 点的技术讨论
- 周末消息量减少
- 临近 deadline 消息量增加

### 9.4 渐进式

- 知识和技术讨论要体现学习曲线
- 不要一开始就全知全能
- 问题和 bug 要真实
- 解决方案要合理

### 9.5 冲突适度

- 冲突要真实但不激烈
- 最终都要有解决方案
- 不要有伤害性的言论
- 体现团队协作

### 9.6 废话比例

- 约 15-20% 的消息是非技术性的闲聊
- 闲聊内容要真实（食堂、考试、段子等）
- 闲聊时间要合理（周五下午、阶段性突破后等）
