# feishu-agent-mem 评测方案 — 问题与缺口分析

> 本文档对照 **Agent 评测四维框架（任务达成、执行过程、性能成本、鲁棒安全）**
> 审视 `docs/evaluation-plan.md` 的缺口和不足，并提出补充建议。

---

## 缺口 1：缺少"任务达成率"聚合指标

### 问题描述

原方案按组件（Lark Adapters / Signal Engine / LLM Agent / Pipeline ...）分别定义指标，但没有从**整体 Agent 任务**的角度聚合：
- 系统每轮检测周期，算一次"任务"，正确完成全部链路（检测→提取→存储→同步）的比例是多少？
- 没有 **Pass Rate (通过率)**：N 次检测周期中完全正确的比例
- 没有 **Progress Rate (完成度)**：部分失败时的完成百分比（如决策提取成功但主题分类错误，算 60% 完成）

### 缺口等级

**严重** — 没有顶层聚合指标，无法回答"这个 Agent 到底靠不靠谱"

### 补充建议

新增整体聚合指标：

| 指标 | 定义 | 计算方式 | 目标 |
|------|------|----------|------|
| 任务通过率 (Pass Rate) | N 次检测周期中完全正确的比例 | 通过数 / 总周期数 | > 85% |
| 任务完成度 (Progress Rate) | 部分失败时的加权完成百分比 | 各子任务加权求和（检测 20% + 提取 30% + 分类 15% + 存储 20% + 同步 15%） | > 90% |
| 场景通过率 (Scenario Pass Rate) | 按场景类型聚合的通过率 | 按 IM/Docs/VC/跨源 分别计算 | 各 > 80% |

## 缺口 2：工具调用评测完全缺失

### 问题描述

这是最严重的缺口。MCP Server 暴露了 8 个工具（search / topic / decision / extract_decision / classify_topic / detect_crosstopic / check_conflict / timeline），但原方案：
- 只测了协议合规（JSON-RPC 格式对不对）和延迟
- **完全没有评测工具选择的准确性** — 给定一个用户意图，Agent 是否选对了工具？
- **完全没有评测参数传递准确性** — 参数名和类型是否正确？
- **完全没有评测工具调用幻觉** — 是否调用了不存在的工具或参数？

当前这个缺口意味着：即使 Agent 的回答看起来正确，也无法判断它是否以正确的方式使用了工具。

### 缺口等级

**严重** — Agent 评测的核心就是工具调用，这方面完全是空白

### 补充建议

新增工具调用评测维度：

| 指标 | 定义 | 评测方法 | 目标 |
|------|------|----------|------|
| 工具选择准确率 | 给定意图选对工具的比例 | 构造 50 个意图→正确工具的映射测试集 | > 95% |
| 参数准确率 | 调用时参数名和值类型正确的比例 | 对比实际参数与期望参数的匹配度 | > 90% |
| 工具调用幻觉率 | 调用不存在的工具或参数的比例 | 审计所有工具调用日志 | 0% |
| 工具调用覆盖率 | 8 个工具在测试中被覆盖的比例 | 统计测试用例覆盖的工具数 | 100%（8/8） |
| Gold Tool Call Match | 实际调用序列与标准序列的匹配度 | Levenshtein 距离 / 精确匹配 | > 80% |

新增测试用例示例：

```json
{
  "id": "TC-TOOL-001",
  "user_intent": "查找所有数据库架构相关的决策",
  "expected_tool": "search",
  "expected_params": { "query": "数据库", "topic": "数据库架构" },
  "expected_tool_sequence": ["search"]
}
```

```json
{
  "id": "TC-TOOL-002",
  "user_intent": "帮我提取这条消息中的决策：'我们决定用 Go 重写后端'",
  "expected_tool": "extract_decision",
  "expected_params": { "content": "我们决定用 Go 重写后端" },
  "expected_tool_sequence": ["extract_decision", "classify_topic"]
}
```

## 缺口 3：缺少推理链评测

### 问题描述

MemoryAgent 的工作流程是一条推理链：

```
Detect Change → EnhancedDetector.Score → 
  [if High/Medium] → LLM.ExtractDecision → 
  ClassifyTopic → DetectCrossTopic → ResolveConflict → 
  PipelineEngine.ApplyMutation
```

原方案把每个步骤拆开单独测（提取准确率、分类准确率等），但没有测**整条链的联合成功率**：
- 每一步都正确才算成功，只要一步出错整体就失败
- 没有"链式失败分析"——哪一步最容易断？
- Agent "走回头路"的能力：第一次分类错了，后续发现矛盾后能否自我修正？

### 缺口等级

**高** — 链式评测是 Agent 评测区别于传统 LLM 评测的关键

### 补充建议

新增推理链指标：

| 指标 | 定义 | 目标 |
|------|------|------|
| 推理链完整成功率 | 从检测到存储全链路无差错的比例 | > 75% |
| 最弱环节分析 | 记录每一步的通过率，定位瓶颈 | 各步 > 85% |
| 多步修正率 | 后续步骤纠正前序错误的次数占比 | > 10%（允许修正） |
| 平均推理深度 | 一次完整决策从检测到存储经过的步骤数 | 基准值 |

## 缺口 4：缺少执行轨迹 (Trajectory) 评测

### 问题描述

原方案完全没有"执行轨迹"的概念：
- 没有定义 **Gold Trajectory（标准执行路径）**
- 没有 **Trajectory Match（轨迹匹配度）** — Agent 实际走的路径和期望路径的偏离程度
- 没有 **冗余步数** — Agent 是否做了不必要的 LLM 调用或工具调用

对于这个系统，一个典型的 Gold Trajectory 示例：

```
IM轮询 → DetectResult有变更 → WorkerPool调度 → 
EnhancedDetector评分(>0.65) → SignalActivationEngine触发 → 
LLM.ExtractDecision成功 → ClassifyTopic → 
PipelineEngine.ApplyMutation → Git写入 → Bitable同步
```

如果 Agent 走了弯路（如：评分低于阈值但 LLM 仍尝试提取→失败→再试），就是轨迹偏离。

### 缺口等级

**高** — 无法判断执行效率，也无法发现冗余调用造成的成本浪费

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 轨迹精确匹配率 | 完全按 Gold Trajectory 执行的比例 | > 70% |
| 轨迹编辑距离 | 实际路径与 Gold 路径的差异步数 | < 2 步 |
| 冗余 LLM 调用率 | 不必要的 LLM 调用占总调用的比例 | < 10% |
| 冗余工具调用率 | 不必要的工具调用占总调用的比例 | < 5% |

## 缺口 5：Token 消耗与成本审计缺失

### 问题描述

原方案只有一句"LLM Cost Per Extraction < 4000 tokens"，对于 Agent 系统来说太粗糙：
- Agent 会多次调用 LLM（提取 + 分类 + 跨主题 + 冲突检测 + 可能的降级回退），需要 **per-task** 总 token 审计
- 没有 **单位有效决策的 token 成本** — 花多少 token 才能成功存储一个决策？
- 没有 **浪费 token 分析** — 失败的 LLM 调用（解析失败、超时、幻觉）浪费了多少 token？
- 如果用 Doubao 或 DeepSeek 的不同定价，成本差异没有评估

### 缺口等级

**中高** — 影响商业化落地判断

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 每任务总 token 消耗 | 一次决策从检测到存储的累计 token（含重试） | < 15000 tokens |
| 单位有效决策 token 成本 | 总 token / 成功存储的决策数 | < 8000 tokens/决策 |
| 浪费 token 率 | 失败调用 token / 总 token | < 15% |
| 降级节省 token 比 | 使用 fallback 比 LLM 节省的 token 比例 | > 60% |
| 推理链各环节 token 分布 | Extract/Classify/CrossTopic/Conflict 各占多少 | 基准值 |

---

## 缺口 6：循环 / 死循环检测缺失

### 问题描述

系统有多处循环：
- **检测轮询循环**：每 N 秒轮询一次，检测到同一变更会重复处理吗？
- **LLM 重试循环**：调用失败时重试，指数退避是否正确？达到最大重试次数后是否停止？
- **Worker Pool 处理循环**：工作池消费作业队列，可能生产速度 > 消费速度导致堆积
- **去重循环**：同一内容被多次检测到，去重机制能否防止无限循环？

原方案完全没有针对这些循环的收敛性测试。

### 缺口等级

**中高** — 死循环会导致无限 token 消耗和系统崩溃

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 轮询去重率 | 连续 N 次轮询中同一变更被重复处理的次数 | 0（N=10） |
| LLM 重试收敛率 | 重试达到最大次数后正确停止的比例 | 100% |
| 工作池队列积压率 | 高峰时队列长度 / 队列容量 | < 80% |
| 最大循环深度 | 一次变更触发的最大处理轮数 | ≤ 5 轮 |
| 循环检测覆盖率 | 代码中所有 for/loop 被测试覆盖的比例 | > 90% |

---

## 缺口 7：错误恢复能力缺乏量化指标

### 问题描述

原方案在对抗测试中提到了"网络故障"场景，但只验证了"回滚"，缺乏对整个错误恢复能力的量化评测：

- **自我修正能力**：LLM 第一次返回畸形 JSON → 重试 → 第二次返回正确结果，这个"自救"能力没有指标
- **优雅降级阶梯**：LLM 不可用 → fallback 关键词提取 → 降级提取，这个降级阶梯的流畅度和成功率没有评测
- **跨适配器故障隔离**：VC API 挂了 → IM 还能工作，原方案只提了一句"优雅降级"但没有量化
- **恢复后一致性**：飞书 API 从故障恢复后，系统能否正确追上漏掉的变更？

### 缺口等级

**中高** — 生产环境必选项，故障不可避免，关键看恢复能力

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 首次重试成功率 | 第一次重试就成功的比例（LLM / API） | > 60% |
| 完全恢复率 | 故障后 N 分钟内系统恢复到正常状态的比例 | > 95%（N=5） |
| 降级覆盖率 | LLM 不可用时 fallback 覆盖决策类型的比例 | > 80% |
| 故障隔离率 | 单适配器故障影响其他适配器的事件数 | 0 |
| 追赶成功率 | 故障恢复后能正确追上遗漏变更的比例 | > 90% |

## 缺口 8：LLM 输出稳定性（一致性）未评测

### 问题描述

LLM 输出有随机性（即使 temperature=0，不同模型版本、不同请求间也可能有差异）。原方案缺乏：
- **同一输入多次运行的结果稳定性**：同一个决策文本，跑 10 次提取，结果是否一致？
- **主题分类漂移**：同一决策文本在短时间内多次分类，主题是否会变？
- **跨模型一致性**：用 Doubao vs DeepSeek，提取结果有多大差异？

### 缺口等级

**中** — 影响可靠性和用户体验

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 提取一致性 | 同一输入 N 次提取结果完全相同的比例 | > 90%（N=10） |
| 分类稳定性 | 同一输入 N 次分类得到相同主题的比例 | > 95%（N=10） |
| 冲突评分方差 | 同一对决策 N 次冲突评分的标准差 | < 0.1（N=10） |
| 跨模型一致性 | 不同 LLM 提取结果的一致比例 | > 80%（Doubao vs DeepSeek） |

## 缺口 9：规则合规性未评测

### 问题描述

系统是否有隐含或显式的规则约束？例如：
- 不处理 `deprecated` / `archived` 状态的决策
- 不覆盖已被人工确认的决策
- 不提取来自黑名单频道/用户的消息
- 不在非工作时间执行写操作

原方案完全没有规则合规性评测。

### 缺口等级

**中** — 企业内部流程自动化时尤其重要

### 补充建议

| 指标 | 定义 | 目标 |
|------|------|------|
| 禁令违反率 | 违反预设规则的操作次数 / 总操作数 | 0% |
| 状态守卫违反率 | 对 archived/deprecated 决策执行写操作的比例 | 0% |
| 权限边界违反率 | 越权访问数据的比例 | 0% |
| 合规检查覆盖率 | 所有预设规则都有对应测试用例 | 100% |

## 缺口 10：缺少 LLM-as-a-Judge 评测方法

### 问题描述

原方案只有两种评测方法：
- **Code-based**（硬编码断言）— 适合客观事实校验
- **Human-in-the-loop**（人工标注）— 成本高、不可扩展

缺少 **LLM-as-a-Judge** — 用更强的模型（如 GPT-4o 或 Claude 4）来自动评估 Agent 的输出质量。

适用场景：
- 决策提取质量评估（提取的决策是否准确、完整）
- 主题分类合理性（给定上下文，这个主题是否合理）
- 执行轨迹质量（Agent 走的路径是否合理）
- 回复质量（MCP 响应是否清晰有用）

### 缺口等级

**中** — 人工标注无法规模化，LLM-as-a-Judge 是关键补充

### 补充建议

| 评测场景 | Judge 模型 | 评分维度 | 与人工一致率目标 |
|----------|-----------|----------|----------------|
| 决策提取质量 | GPT-4o / Claude 4 | 准确性、完整性、简洁性（1-5 分） | > 85% |
| 主题分类合理性 | GPT-4o / Claude 4 | 合理、边缘、不合理（三分类） | > 90% |
| 工具调用正确性 | GPT-4o / Claude 4 | 正确、部分正确、错误（三分类） | > 90% |
| 轨迹合理性 | GPT-4o / Claude 4 | 高效、可接受、绕路、错误（四分类） | > 80% |

## 缺口 11：Golden Set 结构不完整

### 问题描述

原方案有 Ground Truth 数据集的计划（500 条决策语料），但缺少 Agent 评测需要的 Golden Set 结构。一个完整的 Golden Set 条目应该包含：

```json
// 原方案的结构（只有输入 + 预期输出）
{
  "text": "我们决定使用PostgreSQL",
  "is_decision": true,
  "expected_topic": "数据库架构"
}

// Agent Golden Set 需要补充的结构
{
  "id": "GS-001",
  "difficulty": "easy",              // 难度分层
  "user_instruction": "...",         // 用户指令 / 触发条件
  "expected_final_state": {          // 期望最终状态
    "git_commit_exists": true,
    "bitable_record_exists": true,
    "decision_title": "...",
    "decision_status": "active"
  },
  "expected_tool_sequence": [        // 期望工具调用顺序
    "search", "classify_topic"
  ],
  "scenario_type": "im|doc|vc|...", // 场景类型
  "anti_check": false,               // 是否反信号测试
  "error_injection": null            // 是否注入故障
}
```

### 缺口等级

**中** — 影响评测的代表性和可复现性

### 补充建议

Golden Set 条目数量扩展并分层：

| 难度 | 数量 | 说明 |
|------|------|------|
| easy | 200 | 显式决策，单源，无干扰 |
| medium | 150 | 隐式决策，跨源，有噪声 |
| hard | 100 | 模糊决策，多源冲突，需推理 |
| adversarial | 50 | 边界情况、注入攻击、故障注入 |

## 缺口 12：缺少评测报告与持续追踪机制

### 问题描述

原方案只定义了"什么时候跑测试"，但没有定义：
- **评测报告的详细输出格式** — 每次评测输出什么？
- **历史趋势追踪** — 本次跑分和上周跑分对比如何？
- **回归告警** — 哪项指标下降了？降了多少？
- **可视化** — 报告通过什么形式展示？

### 缺口等级

**中** — 影响评测结果的可消费性和可操作性

### 补充建议

定义标准评测报告格式：

```json
{
  "report_id": "EVAL-20260504-001",

    "avg_tokens_per_task": 4200,
    "avg_latency_ms": 3500

  "tool_call_metrics": { ... },
```

## 总结：原方案与 Agent 评测框架的对照表

| Agent 评测维度 | 原方案覆盖度 | 关键缺失 |
|---------------|-------------|---------|
| **1. 任务达成** | 低 | 无 Pass Rate / Progress Rate 聚合指标；场景测试无通过率定义 |
| **2. 工具调用** | 极低 | 无工具选择/参数/幻觉评测；8 个工具无调用准确率指标 |
| **3. 推理规划** | 低 | 无推理链联合成功率；无最弱环节分析 |
| **4. 执行轨迹** | 无 | 无 Gold Trajectory 定义；无轨迹匹配度；无冗余步数审计 |
| **5. 性能成本** | 中 | Token 审计粒度太粗；无单位决策成本；无浪费分析 |
| **6. 循环检测** | 无 | 无轮询去重率；无重试收敛率；无工作池积压测试 |
| **7. 错误恢复** | 低 | 无首次重试成功率；无完全恢复率；无故障隔离量化 |
| **8. 输出一致性** | 无 | 无多次运行稳定性指标；无跨模型一致性 |
| **9. 规则合规** | 无 | 无禁令检测；无状态守卫；无权限边界测试 |
| **10. 评测方法** | 中 | 缺少 LLM-as-a-Judge；人工标注不可扩展 |
| **11. Golden Set** | 低 | 缺少难度分层、用户指令、期望工具序列字段 |
| **12. 报告追踪** | 无 | 无标准报告格式；无历史趋势；无回归告警 |

### 优先修复清单

按严重性和实施难度排序：
